# English World PRD

独立维护正式产品需求。用户说“写一个 PRD”即可使用；完成需求阶段后停止。完整研发流程由 [english-world-delivery](../english-world-delivery/SKILL.md) 调用本 skill，再衔接设计、Spec Kit 和验收。

## 定位与输入

定位含 `docs/prd/README.md` 的 react-font 仓库，读取适用 AGENTS、相关项目记忆和工作树状态，保留无关改动。路径相对此仓库。

先读取 `docs/prd/README.md`、`docs/prd/index.json`、对应模块入口、现有功能正文、同目录补充和决策。判断创建、修改、审核或批量整理；用户已有明确范围时直接执行，不重复询问工作模式。

使用可用的 `bmad-prd` 进行需求梳理和审核，其默认日期目录和输出位置服从以下项目约定。它不可用时按本 skill 完成整理并如实说明，不能声称已执行 BMAD。

## 唯一来源与需求保留

- 模块入口为 `docs/prd/<module>/prd.md`；功能正文为 `docs/prd/<module>/features/<feature>/prd.md`。已登记的正式来源保留原址，迁移需同步引用，不能复制出第二份有效正文。
- 使用稳定模块和功能 ID。更新模块入口及 index.json 的主要/关联模块映射；跨模块需求只有一份正文。
- 整理前列出源正文、补充、决策与历史输入。逐条建立旧条款到新条款的对应清单；无编号的规则也要覆盖。批量整理将清单和未决项保存在 `docs/prd/maintenance/`，明确属于维护证据，不是产品需求正文。
- 保留原 FR/AC 编号；引用为 `<module>/<feature>/AC-01`。重复合并保留所有来源，复合条款拆分需保留映射与完整语义；不因统一标题删除异常、权限、边界或非功能要求。
- 冲突只有明确批准的修订才能覆盖。未知规则标待确认，区分来源事实、用户决定、建议和假设；不能从代码或测试反推已批准需求。
- 历史 `docs/superpowers/prds/` 和工作区交付目录不再新增正式正文。现有跳转、migration.json、测试来源和设计/Spec引用受路径变化影响时一起核对。

## 正文写作

按复杂度采用一致阅读顺序：背景与目标 → 用户角色与端 → 范围/非目标 → 用户流程 → 功能需求 → 业务规则、字段与状态 → 权限与异常恢复 → 非功能约束 → 验收标准 → 来源、决策和待决项。小改动可合并无关章节，不填空架子。

功能需求使用稳定 FR；AC 应能观察并验证结果，覆盖适用的正常、等待、空态、失败、重试、刷新恢复、权限和数据归属。原文细节不适合正文时移至同目录补充并显式链接，不静默删减。

PRD描述业务目标与行为；技术机制、UI设计、Spec、实施计划和运行证据留在各自目录，通过链接关联。需求状态与实现/测试/部署状态分别表达；不把 `final` 当作已上线或通过验收。

## 审核与完成

核对全部来源条款映射，检查遗漏、重复、冲突、不可执行验收及断链。模块只有局部需求时明确覆盖缺口，不宣称完整基线。审核请求默认只报告；修改/整理请求在授权范围直接修正文档，产品决定有冲突时列出待决项并继续无关工作。

维护同目录 `.decision-log.md`，记录本轮依据、改动、未决项和批准来源；历史决策的重建标为追溯推断，不伪造批准。未解决的问题保留真实状态，不自动标 final。

检查索引、模块入口与正文一致，引用路径真实存在，需求保留清单无未解释遗漏。管理端使用正式来源的生成目录；按项目当前生成/检查命令同步并验证，不直接编辑生成文件或冒称线上已同步。

最终给出正文路径、整理范围、需求保留核对、冲突/缺口与验证结果。仅写 PRD 不自动创建 delivery/request、设计、Spec 或测试运行，不进入开发、提交、推送和发布。若来自完整交付，返回正式路径、稳定 ID 和待决项，由调用方维护交付记录。

## 当前研发端范围

后续研发默认仅覆盖电脑端学生端与管理端，不包含移动端；只有用户明确重新纳入时才增加移动端需求、设计、实现和验收。历史移动端条款保留来源并标注不在当前研发范围，不静默删除，也不作为当前交付的必验项。
