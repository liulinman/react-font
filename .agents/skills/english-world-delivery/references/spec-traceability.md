# Spec Kit、设计输入与测试追踪

规格阶段或需求/设计变更时读取。所有路径按实际前端仓库；后端独立记录版本。

## 准备工具，不伪造集成

先读项目AGENTS、当前Spec Kit配置/安装记录及可用命令；典型线索 `.specify/`、`specs/`，目录存在不等于CLI可用或已固定版本。执行真实命令并读输出，不能从模板文件名推断阶段通过。

需安装时，仅增加本次授权交付所必需的项目级依赖/集成并记录文件差异；不顺手全局安装、替换模型配置、设置Secrets或重置其他工具。初始化先预览可能覆盖的文件，保留既有规则，破坏性覆盖另行澄清。按当前授权读取官方文档 https://github.com/github/spec-kit ，选择和记录固定版本/commit及Codex集成；初始化前检查会覆盖的现有配置，不擅自重置已有规则。缺运行时/凭据时准确报告，完成独立准备工作。不得用模拟命令输出或手写模板冒充Spec Kit执行。

BMAD负责产品PRD；Spec Kit负责spec/clarify/checklist/plan/tasks/analyze等实际版本提供的工作流。不机械重复同一阶段，多数新功能需先将确认PRD和设计输入整理给spec，再进行有必要的澄清与一致性检查。没有产品歧义时无需为流程而重复提问。

## 来源与目录

- PRD：`docs/prd/<module>/features/<feature>/prd.md` 和正式决定补充，由PRD索引定位。不能为Spec Kit再复制同级业务来源。
- UI设计：已确认的 `docs/design/<module>/<feature>/design.md`、关键状态与原型/设计工具版本。纯后端标不适用及原因。
- Spec Kit：复用已有布局；否则 `specs/<编号>-<feature>/spec.md`、质量清单、`plan.md`、`tasks.md`。
- 追踪侧车：同一规格目录 `traceability.json`，用于当前项目的映射和来源冻结。这不是Spec Kit或现有测试执行器默认支持的字段。

每份规格记录稳定feature ID、本轮范围、PRD/设计源路径及摘要、确认依据、产品约束、验收场景与未决假设。Spec引用原FR/AC并保留原意；计划承接跨前后端落点、依赖和验证任务。

## 映射的最低内容

逐条记录：PRD命名空间和子条款、设计状态（如适用）、稳定Spec场景ID、Case ID、suite ID与完整test名、验证方式与证据等级。一个复合AC可对应多条场景与Case，不因其中一条通过判整个AC通过。

源信息同时涵盖PRD/决策、设计、Spec及两个仓库的受测版本。明确dirty工作树摘要。不要给截图或输出随意加hash后称“来源已验证”；必须从实际文件/设计版本取得摘要并核对内容对应关系。

## 与现有Case系统兼容

继续用 `docs/testing/cases/<module>/<feature>.json`、`docs/testing/suites.json` 和现有精确binding；先读schema与执行器。

- schema已支持Spec/设计引用：按真实字段接入并验证冻结计划、过期检测、结果聚合和报告。
- 不支持：先用侧车映射与人工逐项核对，明确“执行器尚不自动计算Spec覆盖”。不要向严格schema硬塞字段，也不能输出编造的自动覆盖率。
- 用户授权接入执行器时，才实现schema/校验/计划/报告链路，并为未绑定、过期、跳过/失败、一个条款多个子场景等情况验证聚合；不能只给Case加字段就称集成完成。

来源变化后按映射识别受影响场景/Case，复核语义并重跑适用项。设计改变不必重新测试所有不相关后端逻辑，但影响角色/业务规则时先修订PRD与Spec。旧证据保留，仅失去支持新版本结论的资格。

## 覆盖结论口径

分母是本轮冻结范围中已盘点的PRD原子子条款/Spec场景，不是已写Case总数。逐项区分完整合格、部分、失败、跳过、未执行、未绑定与来源缺口；同一条款需要的多个Case或人工项全部有合格证据才完整覆盖。侧车人工核对明确标“人工映射复核”，不冒称执行器自动计算。分母或条款拆分仍未确认时报告明细及缺口，不输出伪精确百分比。
