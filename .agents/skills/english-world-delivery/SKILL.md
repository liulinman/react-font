# Freewing：需求、设计、规格到交付

默认链路：需求输入 → BMAD PRD → UI/交互设计与确认 → Spec Kit Spec/计划/任务 → AI实现与审查 → 功能及视觉/交互验收 → Cloud与完整证据归档 → 获授权的提交/发布。

此skill编排项目已有工具，不意味着Spec Kit、远端runner或长期归档已经接通。按请求起止阶段执行；纯后端等没有UI影响的任务，说明依据后跳过设计，不制造原型。

## 范围、授权与恢复

以下业务阶段仅在实际交付请求中执行。若当前请求仅创建/更新本skill，则只改skill及必要支持资源并做安全演练，不创建项目request/delivery记录，不启动安装、原型、研发或发布。

- 定位包含 `react-font/` 与 `nestjs/` 的工作区，读取适用AGENTS与相关项目记忆，检查两仓库状态，保留无关改动。项目路径以当前工作区为准。
- 记录功能、稳定模块/feature ID、端与角色、起止阶段、两仓库基线/dirty、已获授权。现有确认可复用，不因阶段切换反复审批；只澄清会改变产品行为、设计方向或发布权限的缺口，继续不依赖答案的工作。
- “创建/更新skill”只授权改skill；“研发/测试”不自动授权提交、push或部署。已有明确授权继续执行。push前检查实际CI触发及部署副作用，不能以“只push”掩盖生产发布。
- 将原始输入、未决点与确认依据记录在本轮交付目录的 `request.md` 和 `delivery.md`，不复制一份正式PRD。已有目录优先；否则 `react-font/docs/delivery/<日期>-<feature>/`。用 [交付记录](references/delivery-record.md) 追踪状态和证据。实际交付同时遵守 [产物位置与流程追溯](references/artifact-locations.md) 和 [管理端功能流程数据](references/feature-records.md)：PRD、Spec、原型图/可点击原型及每次测试结果都有固定归属，必须回链本轮delivery和持久索引，不得仅留聊天或临时URL。实际交付维护结构化 `delivery.json`、`docs/delivery/index.json` 与每次run清单，使用稳定featureId/changeId/runId；可读delivery.md链接这些真实资料，供未来管理端追溯。不得把格式规则写入误称管理端接口已实现。
- 状态使用 `pending/running/passed/failed/blocked/skipped`；按实际证据更新。新输入使相关PRD、设计、Spec或Case过期时，定位影响后复核，不能只改摘要消除提示。修复重跑保留旧run，不覆盖失败证据。

## 1. 用 BMAD 整理、审核 PRD

读取项目内 [english-world-prd](../english-world-prd/SKILL.md)，按其规则创建、更新或审核正式 PRD。该 skill 是独立入口，负责正文、需求保留核对、决策、模块入口和索引；本流程不再维护另一套 PRD 写作规则。

已有有效 PRD 时按本轮变更检查来源与待决项，再进入设计或指定阶段；用户只要求写/改/审核 PRD 时转入该 skill，完成后停止，不创建完整交付记录或继续研发。确认需求状态不代表已实现、已验收或上线。

## 2. UI/交互设计与确认

有UI影响时读取 [UI设计与客户体验](references/ui-design.md)。以客户要完成的任务组织页面，不把“去AI味”当成换配色，也不强迫所有界面采用大胆展示风格。

主工具是项目本地Impeccable，UI UX Pro Max仅提供有需要的参考，Vercel Web Interface Guidelines负责适用的交互/无障碍检查。读取各自实际SKILL，遵守固定版本和项目设计事实；缺少工具时查明并报告，不冒称已调用。用户指定Figma时使用对应可用skill，不强制额外设计平台。

沿用现有设计系统、品牌、组件和成功交互，覆盖主流程、加载、空态、错误、重试、禁用/权限及破坏性确认。交付设计说明、相关关键状态和可点击原型；对已有明确设计的小改动可用聚焦状态示例/设计diff代替整套原型。放在 `docs/design/<module>/<feature>/` 或项目已有设计目录，通过路径/版本与PRD相连。

需要用户选择或确认视觉方向时，先做可审阅的隔离原型再请求确认；未确认不把新视觉方案写进生产页面。已获确认的设计和用户明确放权的细节不重复询问；若PRD明确规定了布局或客户指定稿，直接遵循。纯原型限合成数据、不接生产写入，不冒充业务实现。

## 3. 用 Spec Kit 写规格、计划和任务

读取 [规格与双来源追踪](references/spec-traceability.md)。先核实项目Spec Kit安装、固定版本、集成方式和可用命令；缺失时在当前任务允许的范围准备项目级接入，安装与初始化改变的文件单独记录。只参考模板不能称为跑过Spec Kit；无法接入时交付标明的草稿/待办，不能冒称阶段完成。已有有效Spec或用户仅指定独立修复/测试时，按实际输入完成该范围并记录依据；新功能仍缺必要规格时，只推进不依赖该缺口的工作，不自行绕过规格门禁。

默认使用 `react-font/specs/<编号>-<feature>/`，项目已有Spec Kit布局则复用。以确认PRD与UI设计为输入，生成 `spec.md`、质量检查、`plan.md`、`tasks.md`；按实际版本执行澄清、一致性与覆盖分析。PRD仍是业务来源，设计是确认的交互/视觉依据，Spec定义本次开发可验证契约，plan/tasks说明实现。

记录PRD与设计来源/摘要，逐项映射FR/AC→设计状态→Spec场景。模型推断必须标明；Spec不能私改业务，设计不能取消服务端权限。把所有关键矛盾和未决产品决定解决后再进入依赖它们的实现；不阻断无关工作。

## 4. AI 实现与代码审查

AI读取PRD、确认设计、Spec、plan/tasks与仓库规则，按本轮范围修改学生端、管理端或后端。从需求/规格得出测试预期，不能照当前实现反向生成永远通过的断言。设计已确认后先落一条完整任务路径，再按任务补全；不是只实现截图。

运行受影响层的检查/构建及有意义的测试，审阅整个任务diff，核对权限、异步竞态、输入边界与兼容性。发现缺陷修复后验证；不能因测试失败放宽已确认要求。说明自审或实际独立审查，不伪造独立结论。

功能、接口、配置、交互或部署变化按项目 `.agents/skills/english-world-docs-maintenance/SKILL.md` 同步公开教程，保持知识/实现/实例；内部PRD、Spec、设计和日志不导入公开站点。没有影响时说明依据。未提交工作树不得冒认为HEAD来源的代码片段。

## 5. 自动化、视觉/交互验收与失败分析

执行项目 `.agents/skills/english-world-prd-testing/SKILL.md` 和 `docs/testing/prd-testing.md`；入口区别见 [项目执行与发布](references/project-release.md)。复用Case、suite绑定及隔离执行器，不另造测试平台。

- Case覆盖PRD所有本次子条款与Spec场景，相关UI行为另指向确认的设计状态；使用精确suite/test名。按 [追踪规则](references/spec-traceability.md) 记录双来源，不向不支持的schema硬塞字段。
- 初始化候选、draft、缺绑定、跳过、mock、未执行均不算真实验收。外部AI替身不证明真实生成/语音质量；真实付费验证按任务授权与预算。
- 使用一次性测试库与合成账号；不对生产seed。后台AI在副本生成Case/脚本时审查允许路径、保留既有内容，再合入并对最终版本重跑；等待实际任务完成后读取本次结果。
- UI实现后按确认设计在真实浏览器完成客户任务，验证关键状态、键盘/焦点、文案/恢复及本次要求的视口；截图、操作与问题整改记录见 [UI设计验收](references/ui-design.md)。自动截图存在不等于视觉通过，不以像素完全相等替代可用性判断。
- AI读取当前计划、结果、断言、日志与截图，按 `product/test/environment/unknown` 分类；根因不确定明确标注。修复后新run关联旧run，不能删除首次失败或静默降低断言。

阶段结论分别报告：执行通过率、PRD覆盖、Spec覆盖、设计符合性、人工/供应商待验项和AI分析状态。测试全绿但漏测或关键体验未验，不能说全量验收通过。

## 6. Cloud 与完整报告归档

读取 [证据与Cloud](references/evidence-cloud.md)。默认记录Cypress Cloud，除非用户明确仅本地；只有工具实际返回本次run URL并核实结果才记上传成功。失败不静默降级。

Cloud保存浏览器执行记录及配置支持的媒体；完整PRD/Spec/设计映射、其他层测试报告和AI分析单独归档。保存两仓库版本/dirty补丁摘要、来源摘要、run ID、Cloud URL与证据包地址，不能把当前HEAD当成未提交代码的来源。未配置远端runner或长期存储时如实保留待办，不承诺永久留存或关机后本机任务继续。

## 7. 提交与 push

通过本轮要求的检查后，按仓库分开审阅并暂存本任务文件，排除密钥、测试账号资料、原始报告、生成缓存和他人改动。测试源码是可维护资产，不因其他项目 skill 的默认规则而排除。没有必要不新增提交钩子、改远程或重写历史。

在授权范围提交；提交后核对 SHA 与工作树，记录两仓库版本对应关系。纯元数据提交无需机械重跑全部；文件内容、测试或依赖变化时重验受影响部分。push 前核对目标远程/分支、包含的全部待推提交与自动部署副作用。

仅推获准分支，不默认 force push，不合并未经授权的发布分支。网络结果不明先读远程状态，避免盲目重做。推送成功仍需跟踪对应 SHA 的 CI，测试失败不忽略、不擅自旁路。当前分支不匹配发布触发条件时使用已授权路径，不把 push 成功称为已部署。

## 8. 部署、验证与恢复

执行前读取 [项目执行与发布](references/project-release.md) 和当前工作流。先准备可审阅的版本、构建/测试证据、目标环境、服务范围与回滚点；已有充分授权继续执行，无授权时只向用户请求这一具体发布动作。

部署已经验证且能追到 SHA 的产物。只更新受影响服务；后端确有改动时单独核实后端发布方式、数据库兼容和前后顺序，不套用“所有任务只发前端”。保留现网 HTTPS、证书、ACME、MCP 配置及业务数据，不照抄历史 IP、镜像 ID 或凭据。

跟踪部署完成，核对线上实际版本、健康状态、本轮关键路径、权限及相关文档/资源；不可用命令退出成功或首页200替代业务验证。写入生产测试数据、真实付费调用等额外动作按实际授权边界处理。客户端旧缓存需验证实际加载版本，不能靠删除用户数据掩盖。

失败停止扩大变更；保留日志，依预先授权且已核实的回滚方案恢复原产物/配置并再验。数据库破坏性回退不能视为普通应用回滚。不能恢复或需要额外权限时，说明当前影响、证据与所需动作，部署状态保持失败/阻塞。

## 完成交付

最终用简短中文给出：PRD、确认UI/原型、Spec与审查记录、实现范围、功能及视觉/交互验收、测试报告与Cloud/完整归档链接、覆盖缺口、两仓库提交及 push/CI 状态、部署环境与实际版本、验证及回滚状态。所有路径与链接必须真实存在。

只有本次请求的各阶段都达到完成条件才能说“全流程完成”。停止在任一授权边界时，交付已完成成果和准确待办；不得用报告生成、push 成功或容器运行冒充验收和上线完成。用户要求保存/换窗口时按项目规则更新 vault 交接，不保存秘密。

## 当前研发端范围

后续研发默认仅覆盖电脑端学生端与管理端，不包含移动端；只有用户明确重新纳入时才增加移动端需求、设计、实现和验收。历史移动端条款保留来源并标注不在当前研发范围，不静默删除，也不作为当前交付的必验项。
