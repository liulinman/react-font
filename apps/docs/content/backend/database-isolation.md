# 数据隔离：账号条件必须进入查询

## 隔离不是界面隐藏

两个用户即使搜索同一个词，也应该只看到各自词库里的结果。如果服务端先查出所有词条、再依赖浏览器隐藏不属于当前用户的行，数据已经越过安全边界。English World 的 MCP 路径把账号身份带进数据库条件，这也是阅读代码时最值得优先核对的地方。授权对应哪个用户，应来自已经验证的服务端主体，而不是来自工具参数中的一个任意 userId。

## 项目的真实条件

`nestjs/src/interface/mcp-access/mcp.service.ts` 的 `word` 查询使用 `{ id, userId: p.user_id }`，`queryWords` 从 `{ userId: p.user_id }` 开始构造条件。覆盖和删除同样把词条 ID 与账号条件组合使用。授权管理按当前登录账号过滤；撤销时 SQL 同时要求授权 ID 与 user_id 匹配，并锁定记录。这些条件意味着“知道另一条记录的编号”不等于有权访问它。

```ts
// 摘自 mcp.service.ts 的词条作用域条件
where: { id, userId: p.user_id }
```

这里 `p` 是服务端认证后的 principal。示例展示条件的来源，不是允许调用者自行构造 principal 的公共 API。SQL 中的替换参数与 ORM 条件用于传值，不能改成把用户输入直接拼接进 SQL 字符串。关键词、limit、offset 也有输入约束；分页限制只能约束返回规模，无法代替账号过滤。

## 权限与隔离是两个检查

账号隔离回答“这是谁的数据”，范围授权回答“能做什么”。`query_words` 和 `get_word` 对应读取范围，新增、覆盖、删除各自要求不同范围。`execute` 在事务中再次锁定并检查授权状态，避免只在请求最初认证时看一次有效期或撤销标记。一个有查询权限的授权不能通过直接调用确认工具获得写权限；一个有写权限的授权也不能跨账号修改数据。

预览凭证还绑定授权、账号、动作与词条快照。用户即使拿到自己的另一枚授权，也不能随意消费由原授权生成的凭证。这样做降低了凭证在不同操作流程里被误用的可能性，但客户端仍应避免把凭证和完整词条发进公开日志。

## 设计一个可复核的验证

在隔离环境准备账号甲、账号乙，各自保存同名演示词。用甲的授权查询，核对每条返回记录归甲所有；再请求乙的词条 ID，预期得到不可访问的业务结果。继续用只读授权调用覆盖预览，确认范围拒绝。最后撤销甲授权后再次调用，确认不能继续读取。记录授权 ID 的脱敏标识即可，不记录原始密钥。

失败分析要针对每条证据：结果为空可能是搜索规范化或分页问题，不能直接证明隔离正确；跨账号读不到一条记录也不能证明所有写入口都安全。至少覆盖单条读取、列表、覆盖、删除和授权管理。数据环境本身也要隔离，详见[本地开发](/start/local-development)。应用测试中的专用数据库与真实词库分开，才能让这些验证既可重复又不伤害用户数据。
