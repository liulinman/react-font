# 一个 NestJS 请求怎样到达业务逻辑

## 路径相同不代表职责相同

浏览器看到的是一个站点地址，服务端处理的却是一串不同职责。Nginx 收到 `/api/mcp-access/tokens` 后剥离 `/api/` 前缀，把剩余路径交给后端；Nest 控制器声明的是 `mcp-access`。排错时先分清外部路径与控制器路径，否则很容易把一个正确代理后的请求误诊为接口缺失。配置依据是前端 `nginx.conf` 与后端 `src/interface/mcp-access/mcp.controller.ts`。

## 启动与通用处理

`nestjs/src/main.ts` 首先导入 `load-env`，生产环境缺少 JWT 签名密钥会直接失败。随后调用 `connectDatabase`，确认数据库连接可用，再创建 Nest 应用。这个顺序让数据库不可用的实例及时暴露问题。Cookie 解析、压缩、CORS 白名单、统一异常过滤器、响应拦截器和全局 ValidationPipe 在这里安装。参数白名单以及拒绝额外字段是入口保护，但 DTO、业务校验和数据库约束仍各有职责，不能认为全局校验自动覆盖所有任意 JSON 对象。

CORS 控制浏览器跨来源访问，不等于账号认证。主入口允许没有 Origin 的请求继续处理，这是命令行客户端常见情况；MCP 控制器还会调用自身的来源判断。设置管理里的创建与撤销进一步要求可信 Origin，并拒绝明确的跨站操作。因此一个正常登录 Cookie 也不能使任意来源的写操作获得通行。

## 管理接口与 MCP 工具分开看

管理控制器使用 `AuthGuard`，从 `req.user.id` 获取账号身份，列表和审计查询也沿用该身份。MCP 控制器则从 `Authorization` 头认证授权，成功后才检查 POST 方法，再创建 SDK 服务和 Streamable HTTP transport。这里使用显式响应对象传递协议响应，不应假定它与普通业务接口拥有完全一样的响应包装。

```text
外部请求：GET https://example.com/api/mcp
没有 Authorization：401 unauthorized
有有效授权但使用不支持的方法：405，Allow: POST
工具执行中的业务错误：协议工具结果包含 isError 与业务 code
```

这些是控制器分支的预期，不是本页刚执行的线上结果。要完成工具调用，应让兼容客户端处理协议初始化，不要仅发一个看似像业务参数的 POST 就认为调用格式正确。

## 如何定位错误层

先在浏览器网络面板记录路径、方法、状态码及不含敏感信息的错误体。404 可能来自代理路径，也可能来自控制器路由；401 应检查登录与授权是否选对入口；403 应检查来源和权限，不能用关闭来源验证解决；405 则优先核对方法。请求到达工具后出现 `forbidden`，说明身份可能有效但缺少对应范围，而不是数据库连不上。

需要验证启动失败时，可检查 `src/database/connect-database.ts` 的异常路径与对应测试；需要验证账号条件，则继续读[数据库隔离](/backend/database-isolation)。日志中保留时间、请求类型和错误类别即可，完整 Bearer、Cookie 与用户词条内容都不适合作为公开排错材料。把传输失败、协议失败与业务拒绝分开记录，通常比重复刷新更快找到真正的问题。
