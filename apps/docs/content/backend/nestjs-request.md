# 一个 NestJS 请求怎样到达业务逻辑

## 路径相同不代表职责相同

浏览器看到的是一个站点地址，服务端处理的却是一串不同职责。Nginx 收到 `/api/mcp-access/tokens` 后剥离 `/api/` 前缀，把剩余路径交给后端；Nest 控制器声明的是 `mcp-access`。排错时先分清外部路径与控制器路径，否则很容易把一个正确代理后的请求误诊为接口缺失。配置依据是前端 `nginx.conf` 与后端 `src/interface/mcp-access/mcp.controller.ts`。

## 启动与通用处理

`nestjs/src/main.ts` 首先导入 `load-env`，生产环境缺少 JWT 签名密钥会直接失败。随后调用 `connectDatabase`，确认数据库连接可用，再创建 Nest 应用。这个顺序让数据库不可用的实例及时暴露问题。Cookie 解析、压缩、CORS 白名单、统一异常过滤器、响应拦截器和全局 ValidationPipe 在这里安装。参数白名单以及拒绝额外字段是入口保护，但 DTO、业务校验和数据库约束仍各有职责，不能认为全局校验自动覆盖所有任意 JSON 对象。

CORS 控制浏览器跨来源访问，不等于账号认证。主入口允许没有 Origin 的请求继续处理，这是命令行客户端常见情况；MCP 控制器还会调用自身的来源判断。设置管理里的创建与撤销进一步要求可信 Origin，并拒绝明确的跨站操作。因此一个正常登录 Cookie 也不能使任意来源的写操作获得通行。

## 管理接口与 MCP 工具分开看

管理控制器使用 `AuthGuard`，从 `req.user.id` 获取账号身份，列表和审计查询也沿用该身份。MCP 控制器则从 `Authorization` 头认证授权，成功后才检查 POST 方法，再创建 SDK 服务和 Streamable HTTP transport。这里使用显式响应对象传递协议响应，不应假定它与普通业务接口拥有完全一样的响应包装。

```text
外部请求：GET https://example.com/api/mcp
没有 Authorization：401 unauthorized
有有效授权但使用不支持的方法：405，Allow: POST
工具执行中的业务错误：协议工具结果包含 isError 与业务 code
```

这些是控制器分支的预期，不是本页刚执行的线上结果。要完成工具调用，应让兼容客户端处理协议初始化，不要仅发一个看似像业务参数的 POST 就认为调用格式正确。

## 如何定位错误层

先在浏览器网络面板记录路径、方法、状态码及不含敏感信息的错误体。404 可能来自代理路径，也可能来自控制器路由；401 应检查登录与授权是否选对入口；403 应检查来源和权限，不能用关闭来源验证解决；405 则优先核对方法。请求到达工具后出现 `forbidden`，说明身份可能有效但缺少对应范围，而不是数据库连不上。

需要验证启动失败时，可检查 `src/database/connect-database.ts` 的异常路径与对应测试；需要验证账号条件，则继续读[数据库隔离](/backend/database-isolation)。日志中保留时间、请求类型和错误类别即可，完整 Bearer、Cookie 与用户词条内容都不适合作为公开排错材料。把传输失败、协议失败与业务拒绝分开记录，通常比重复刷新更快找到真正的问题。

## 账号验证：从表单到服务端状态（本地开发版）

账号入口沿用 `/api/user/`，由 `user.controller.ts` 检查允许字段和输入类型，再交给 `user.service.ts`。登录必须同时提交用户名、密码和图形挑战；图形图片由后端生成，客户端没有正确答案字段。注册先验证邮箱，忘记密码通过注册邮箱验证，修改密码在已登录的设置页验证当前密码。新密码按8～64个Unicode码点校验，支持粘贴；新哈希先使用带版本标记的预哈希，再执行bcrypt，避免长Unicode输入遇到bcrypt字节上限时被静默截断。

图形和邮箱证明存入附加的 `account_challenge` 表，服务端检查用途、归属、时限、消费和发送状态；数据库行锁让并发请求不能重复消费。`account_rate_bucket` 的计数在服务端持久保存，刷新图片、修改前端倒计时或重启单个服务不能重置限制。注册时的用户创建与已验证邮箱归属在同一个事务完成；唯一索引是并发重复注册的最后约束。必要迁移在后端 `migrations/account-access/001-account-access.sql`，应先在隔离库验证，不在请求里自动创建生产表。

清除Cookie只影响当前浏览器。新学习会话带 `authVersion`，服务端每次认证读取 `account_auth_state.session_version`；改密或重置将密码与版本在同一事务更新，因此其他设备的旧学习会话也会被拒绝。管理员Cookie和MCP独立Bearer不使用这一版本，不能把学习端改密误写成撤销所有外部授权。未带新版本的历史学习Cookie需要重新登录；本轮不做历史账号的邮箱补绑或迁移，也不删除历史学习数据。

可在一次性数据库验证：登录两次取得两个学习会话，重置密码后分别请求受保护接口，两个旧会话都应401；新密码可登录、旧密码失败，学习资料不改变。邮件服务使用测试收件替身时，只证明接口与业务集成，不证明公网送达。这些本地开发变更尚未发布。


## 学生头像与管理端选人

桌面学生端在「系统设置 → 个人资料 → 更换头像」上传 5 MB 以内的 PNG、JPG 或 WebP。前端通过 multipart 的 `file` 字段调用 `POST /api/user/avatar`。后端从学习会话确定账号，验证图片内容并重新编码为 128 × 128 的 JPEG，再写入 `user.avatar`。已有数据库需先执行 `migrations/add-user-avatar-storage.sql`，以容纳编码后的头像。上传成功后，当前页面的账号菜单随账号状态一起更新。

「修改昵称」调用 `POST /api/user/display-name`，请求体为 `{"displayName":"小林"}`。昵称接受 1～32 个字符，登录仍用原用户名。已有数据库先执行 `migrations/add-user-display-name.sql`。

例如，老师可用昵称「小林」或原用户名搜索。候选项显示头像和昵称，头像缺失或加载失败时显示昵称首字。选中标签显示「小林」，提交仍使用用户 ID。没有昵称的账号沿用用户名显示。

## 阅读练习：保留原稿的判断题选项

阅读导入保留原稿选项，发布检查需要接受两种雅思判断题：事实判断的 `True / False / Not Given` 和观点判断的 `Yes / No / Not Given`。后端 `src/interface/reading-practice/reading-practice.contract.ts` 与 `reading-workflow.contract.ts` 共用选项检查，比较时忽略大小写和首尾空格，保存时保留原标签。两组都要求肯定、否定、未提及的顺序，不能混用或重排，否则答案下标会失去原意。

例如教学构造的 `options: ["YES", "NO", "NOT GIVEN"]`、`correctIndex: 1` 表示答案为 NO；不能为了通过检查，把原稿改成另一组题型标签。选择第三项仍须说明原文没有建立的信息。选项合法只说明结构通过，来源疑问和教师核对仍需要分别处理，不能自动发布。

### 来源文字核对与检查重跑

阅读审核把“原稿有拼写疑问”和“缺少原稿”分开处理。纯拼写、印刷或OCR文字疑问进入“核对原稿文字”：老师选择当前练习附件，查看原件，填写核对说明与原稿位置/文字依据，再确认与原稿一致。真正缺页、缺图或不可读的材料仍须补充，不能通过这个入口忽略。

后端 `src/interface/reading-practice/reading-review-issues.ts` 集中分类、去重和来源核对绑定，`reading-workflow.service.ts` 在事务内校验草稿修订、原稿归属及可读性，再保存操作者、时间、原稿摘要与内容/附件指纹。确认会更新审核修订以排除在途旧检查，保留有效质量检查状态，但不会发布。改变正文、题目或附件后，原确认失效，需要重新核对。

重新检查替换已过时的普通AI提示，同时保留未核实的来源问题；不能因为模型本轮漏报就视为来源完整。同一内容与原稿已核实的问题不会重复阻断。检查失败不部分提交修复。排查卡住的练习时，先看发布按钮旁的具体原因，再按提示修改内容、核对原稿或补充材料；结构检查通过仍不等于教学内容已审核。
