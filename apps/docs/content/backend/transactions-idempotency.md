# 事务与幂等：让一次确认只产生一次变化

## 两个保证解决不同问题

事务保证一组相关写入共同成功或共同撤回，幂等保证同一意图的重复发送不会重复产生业务效果。网络断开时，客户端往往不知道服务端是否已经完成；简单地再点一次保存，可能让覆盖次数增加两次。Freewing 的 MCP 把词条变化、操作结果、预览消费和成功审计放在事务中，并通过请求编号与凭证结果处理重试。

## 先读事务边界

`nestjs/src/interface/mcp-access/mcp.service.ts` 的 `execute` 使用 `db.transaction`。事务内部锁定当前账号的授权行，重新检查状态与范围，执行工具，更新最近使用时间并写成功审计。异常导致事务回滚；失败审计在外部尽力记录，记录失败不会把原操作伪装成成功。审计不是一个无关的页面附属物，它参与了成功路径的一致性。

`idempotent` 对 action 与 args 的规范化表示计算摘要，再以 token_id 和 request_id 查找已保存结果。如果编号已存在而摘要不同，返回 `request_conflict`；内容相同时返回原结果。新操作成功后把结果写入 `mcp_operation`。因此客户端应为一次用户意图生成一个稳定编号，而不是每次网络尝试都换编号。

```text
第一次：requestId=demo-overwrite-001，参数 A → 写入并保存结果
重试：requestId=demo-overwrite-001，参数 A → 取原结果
误用：requestId=demo-overwrite-001，参数 B → request_conflict
```

## 预览还有第二道保护

覆盖与删除先生成十分钟有效的确认凭证。数据库只保存凭证摘要，并记录账号、授权、动作、词条快照摘要和待应用内容。确认时需要 `confirmed: true`，随后锁定预览行，核对作用域与动作；未消费的凭证还要检查有效期及当前词条是否仍与快照一致。词条变化会得到 `word_changed`，应重新预览让用户看到新的变化，不能自动沿用旧确认。

已经消费的预览保存了原结果，再消费会返回已保存结果。覆盖保留词条 ID 与词头，只合并允许的有效字段，覆盖次数增加一次。新增遇到规范化后同词冲突也不会擅自覆盖。这些是项目业务选择，不能仅凭 MCP 工具声明里的 idempotentHint 就获得；提示是给客户端理解工具性质，真正保证仍在服务端代码和数据库约束里。

## 验证一致性而不是只看响应

有效验证应同时检查最终词条、覆盖计数、预览状态和操作记录。在隔离环境连续提交相同确认，预期结果相同且计数只增加一次；注入成功审计失败后，词条与预览消费都应回滚，再恢复依赖并重试。这里描述验证方法，不能据此宣称当前环境已经通过。

本实现没有展示自动死锁重试循环，业务幂等也不等于数据库会自动重跑全部事务。客户端遇到未知结果应复用原编号并有限重试；遇到明确业务拒绝则纠正输入或重新预览。具体操作过程见[断网重试实例](/backend/retry-example)。
