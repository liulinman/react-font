# 实例：确认覆盖时断网，下一步怎么办

## 问题发生在结果未知的时候

设想你让 AI 补全演示词 example 的解释，预览已经显示旧值与新值，你确认后网络连接断开。此时“没有收到响应”不代表“服务端没有写入”。如果客户端立刻生成一个全新的动作并再次覆盖，用户可能看到重复计数或重复审计。合理处理应保留原意图与请求参数，再让服务端的幂等机制判断是否已完成。

## 先做预览并明确确认

工具输入的结构定义在 `nestjs/src/interface/mcp-access/mcp.controller.ts`，实际写入和结果复用在 `mcp.service.ts`。以下仅是工具层示意；wordId 必须来自当前隔离账号的查询，字段必须通过当前工具 schema。确认凭证由预览响应产生，示例中的占位符不能作为有效凭证发送。

```json
{
  "tool": "preview_update_word",
  "arguments": {
    "wordId": 101,
    "changes": { "englishChinese": "示例；例子" }
  }
}
```

先核对 `before`、`after`、`changedFields` 和 warning。没有变化时服务端会拒绝空覆盖；用户没有确认时不能调用确认工具。确认输入保留为一次意图的稳定对象：

```json
{
  "tool": "confirm_update_word",
  "arguments": {
    "confirmationToken": "<预览返回的凭证>",
    "confirmed": true,
    "requestId": "demo-overwrite-001"
  }
}
```

## 断网后保留哪几样东西

客户端应在当前操作生命周期内保留相同授权、requestId、confirmationToken 和 confirmed 值，有限次数重试同一确认。服务端先用请求编号和载荷摘要寻找原结果；如果原事务已经提交，会返回保存的结果。如果原事务回滚，重试才会重新执行仍然有效的确认。不要自动改词头、修改变化字段或换一枚授权来绕过失败，这些变化已经构成新的业务意图。

同一编号配上不同参数会触发 `request_conflict`。`expired_preview` 表示未消费的预览已过期，需要重新预览；`word_changed` 表示词条在确认前变化，需要重新展示当前差异。`forbidden`、未授权或撤销不是网络暂态错误，继续重复请求没有意义。一般失败也不应无限重试，先检查依赖与服务端日志，再恢复原请求。

## 怎样判断确实只执行一次

在隔离测试库中记录操作前覆盖次数，完成一次成功确认后再发送相同确认，检查两次结果一致，最终次数只比起点增加一。还应验证同一编号换参数会被拒绝，以及预览后另行修改词条会阻止旧确认。测试应使用可丢弃记录，删除工具的永久效果不适合拿真实词库练习。

源码使用事务保存业务结果与成功审计，所以不能只看到 HTTP 成功就宣称幂等成立。要检查工具结果是否 isError，并读数据库最终状态。本文不实现自动重试库，也没有执行付费服务或真实用户写操作；它提供的是可复核的客户端恢复步骤。进一步理解事务回滚与凭证消费，请读[事务与幂等](/backend/transactions-idempotency)。
