# 增量发布与回滚：把变更控制在前端

## 先明确此次发布改变什么

新增公开技术文档与导航属于前端静态交付，可以只更新前端镜像。它不需要重启数据库、重建后端或修改真实学习数据。部署之前先记录现有前端镜像标识、配置摘要及管理端资源摘要，再准备新构建。这些记录使回滚有明确对象，也能证明后端和业务数据没有被本次发布顺手改变。

`react-font/.github/workflows/deploy.yml` 把验证与部署分开：验证阶段安装锁定依赖，运行学生和管理端测试，构建两份产物，再上传供后续部署使用。生产 Dockerfile 消费预构建资源。文档集成应让验证阶段额外构建文档并随同传递，文档构建失败时阻止发布，而不是在生产主机临时忽略错误。实际步骤以当前工作流为准，旧工作流不会自动包含新增目录。

## 为什么不能整套覆盖

既有生产后端可能含有本机工作区没有的模块。前端变更不应成为整套覆盖服务器应用的理由。生产代理又有 HTTPS 443、证书和 ACME 挂载，以及 MCP 的公网连接配置，不能被仓库通用 HTTP 文件覆盖。保留这些不变量，比“容器正在运行”更能说明发布边界正确。

以下是审核清单示例，不是一条可直接执行的服务器脚本：

```text
基线：记录前端镜像、后端镜像、代理配置与证书挂载
输入：已验证的学生、管理端、文档构建产物
动作：仅更新 frontend 服务，保留依赖服务
回滚：恢复基线前端镜像及必要配置，仍只更新 frontend
数据：不做清空、迁移回退或用户记录删除
```

需要远程查看状态时可以用运维配置好的 SSH 别名，例如 `ssh english-world-production`；这个名字只是占位示例，必须先由维护者配置并核对目标。本文没有连接服务器，也没有执行部署命令。

## 上线检查要分层

第一层检查静态文件：文档首页、深层文章刷新、搜索资源、缺失页 404，学生和管理端也应能打开。第二层检查代理与授权：匿名 MCP、授权列表和学习历史不能因为静态站公开而失去保护。第三层检查运行边界：后端镜像、数据库状态、管理资源和 HTTPS 配置与基线一致，续期仍可工作。手机与桌面都要验证导航，旧标签页还要验证更新提示。

公开记录可保留构建版本、检查时间、状态码和脱敏截图。不要上传原始环境文件、服务器私钥、完整登录 Cookie 或带真实用户数据的响应。单次静态页面 200 无法替代所有检查，更不能代表全部 PRD 已通过。

## 回滚也需要验证

发现问题后按已记录的镜像与配置恢复，不要临时猜一个 latest 标签。回滚后再检查 HTTPS、文档路由、管理端与匿名保护，记录恢复版本和残留影响。浏览器可能仍运行旧 Service Worker，服务器回滚不意味着所有标签立即切换；需要结合[旧页面排查](/deploy/stale-page)确认客户端实际使用的版本。静态回滚不应删除新增业务表或用户数据，超出此次范围的后端故障另行处理。
