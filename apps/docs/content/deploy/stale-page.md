# 发布后还是旧页面：从缓存层找到原因

## 同一个地址可能有不同版本

服务器已经发布新静态资源，某个标签却仍然展示旧设置，这种现象不能仅凭一次截图判断是部署失败。HTTP 缓存、已加载的脚本、Service Worker 控制的离线页面和等待激活的新版本，各自都可能保留旧内容。先用无缓存的只读资源请求确认服务器产物，再查看浏览器当前控制器与待更新状态，才能知道问题发生在哪一层。

## 项目里一个具体的可见性缺口

审阅基线时，`apps/english-world/src/App.tsx` 已在全局挂载 `PwaUpdateProvider`。它调用 `virtual:pwa-register` 注册 Service Worker，并在 `onNeedRefresh` 时把状态设为 ready。真正显示“新版本已准备好”的 `PwaUpdatePrompt` 当时只由手机 `MobileAppShell.tsx` 渲染。这意味着桌面同样可能受 Service Worker 控制、收到更新状态，却没有同样明显的操作入口。原因是提示展示范围与注册范围不一致，不能简单解释成桌面从未注册 PWA。

同一基线的 `vite.config.ts` 使用 `/index.html` 作为导航兜底，排除列表只有管理路径。公开文档拥有独立首页，若不把 `/docs/` 排除，旧服务工作线程可能把文档深层导航接回学习平台。Nginx 路由正确仍不足以阻止这个浏览器侧拦截。

## 本次改进应验证什么

文档上线方案要求增加桌面可见的更新提示，并把 `/docs/` 加入 PWA 导航排除规则。这里记录的是变更目标和基线原因；是否已部署到当前访问环境，应由该版本的构建与浏览器证据确认，不能仅凭本文发布就认为所有旧客户端已更新。

更新操作继续沿用活动锁与用户确认：学习活动进行中禁用更新，完成后由用户选择；“稍后”只关闭当前提示，不强制中断。桌面新增提示时还应避免手机出现两份同样的提示。也不能改为一检测到新版本就刷新，否则正在进行的听力或答题可能丢失状态。

## 一次分层排查实例

```text
现象：新标签能看见文档入口，旧桌面标签没有
先查：服务器入口及脚本摘要是否为目标版本
再查：旧标签是否由旧 Service Worker 控制，是否已有 waiting 更新
最后查：桌面提示是否实际挂载，活动锁是否阻止应用更新
```

这套步骤是诊断方法，本文没有在你的浏览器执行。开发者工具可以观察 Service Worker 注册、缓存与网络来源；记录版本和状态即可，不要在截图中带上登录令牌。强制清缓存可以帮助区分缓存问题，却不能作为产品更新机制的最终修复，也不应该要求每个普通用户反复执行。

## 文档导航另做独立验证

更新后的浏览器应能直接访问文档首页，刷新深层文章，并让未知文章保持 404。已有旧 Service Worker 的标签也要走一遍更新流程，确认文档不会跳回平台。服务器与浏览器证据都应保留时间与版本，未执行项明确写未验证。服务端路由基础见[Docker 与 Nginx](/deploy/docker-nginx)，发布与回滚的边界见[增量发布与回滚](/deploy/release-rollback)。
