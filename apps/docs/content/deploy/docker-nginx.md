# Docker 与 Nginx：静态资源和接口怎样分工

## 镜像里放什么决定发布边界

前端生产镜像负责提供学生应用、管理端和公开文档等静态资源，后端镜像负责 API。把两者分开，可以只更新界面而不重启数据库或后端。`Dockerfile.production` 以 Nginx 为运行基础，把已经构建的学生与管理端产物复制进去；安装依赖、测试和构建属于前面的验证阶段。不要把运行容器当作临时开发机安装包，镜像可追溯性会因此丢失。

文档站加入发布链时，也必须把自己的构建产物明确复制到 `/docs/` 对应静态目录，并在上游验证阶段构建成功后才允许打镜像。仅在源码仓库新增 Markdown，不会让已有 COPY 指令自动理解独立站点。相关构建集成应以当前仓库中的 Dockerfile 和工作流为准，不能把本文的目标说明误认为任意旧镜像都已经含文档。

## 四类路径需要不同处理

仓库 `nginx.conf` 把 `/api/` 代理给 backend 服务，并去掉这一前缀；`/admin/` 的深层路由回退到管理端首页；学习平台 SPA 路由回退到学生首页；静态脚本和样式缺失时应返回 404。文档是独立静态站，深层文章路径与真正未知路径也需要自己的规则，不能掉进学习平台的兜底。

```text
/api/mcp                  → 后端 mcp 控制器
/admin/                   → 管理端静态入口
/englishWorld/...         → 学习平台路由
/docs/backend/retry-example → 文档文章
/docs/no-such-page         → 文档 404
```

这里描述访问分工。Nginx location 的匹配优先级会影响最终结果：如果文档没有更明确的匹配规则，请求可能被平台 SPA 的 `location /` 捕获，返回 200 却展示错误页面。若资源文件也被兜底成 HTML，浏览器常报告脚本 MIME 类型错误，根因往往在路由与文件落点而不是代码语法。

## 缓存与代理也影响体验

带内容摘要的脚本适合长缓存，入口 HTML 与 Service Worker 的更新则需要谨慎。Nginx 的静态扩展名规则会影响资源缓存；PWA 还有浏览器内的独立缓存层，两者不能混为一谈。接口代理关闭缓冲并设置较长读取超时，有利于流式请求，但不能据此保证所有客户端、代理与长任务都不会超时。

## 验证一份构建产物

先检查镜像中的三个资源目录与构建版本，再请求首页、文章深链、未知文章和缺失脚本。已知文章应返回正文；未知路径应是 404，不能返回平台 HTML；缺失脚本也不应变成首页。再验证 `/api/` 仍经过代理，匿名访问受保护接口被拒绝。部署检查还要覆盖管理端资源，避免复制静态文件时覆盖原管理目录。

仓库通用 HTTP 配置与生产 HTTPS 配置可能不同，不能用本地文件整份替换线上配置。生产端口、证书挂载、ACME 验证目录和 MCP 公网地址都要保留。相关边界见[HTTPS](/deploy/https)与[增量发布与回滚](/deploy/release-rollback)。
