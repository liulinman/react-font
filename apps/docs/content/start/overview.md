# English World：技术与 AI 实践总结

English World 从个人词库出发，把词条整理、场景听力、阅读和外部 AI 工具接入放进同一套系统。这个项目值得总结的地方，是如何让模型生成的内容经过检查、获得自然发音，再进入用户可操作、可追踪的学习流程。

本文按当前源码总结设计价值与取舍。文中的 effective、演示请求和题目均为教学构造，不是实际模型调用结果；设计存在不等于学习效果已经得到实验验证，也不代表全部需求已经验收。

## 一张图理解系统分工

```text
学习平台：React 页面、看词复习、听力填空、作答反馈
    │ 业务接口
    ▼
NestJS：账号隔离、会话状态、内容检查、权限、用量与并发控制
    ├── DeepSeek：词条校验、场景生成、词形与语义复核
    ├── 豆包语音：单词及完整场景的语音合成
    └── MySQL：业务记录、授权、幂等结果、音频缓存等

支持 MCP 的外部客户端
    │ Streamable HTTP + 独立 Bearer 授权
    ▼
MCP 工具入口 → 受控的词库查询、新增、预览与确认更新/删除
```

前端仓库 `react-font` 使用 pnpm 工作区：学生端在 `apps/english-world`，管理端在 `apps/admin`，公开文档在 `apps/docs`；后端是相邻的 `nestjs` 仓库。下文源码路径分别注明仓库，便于从设计追到实现。

MCP 客户端和平台页面是两种入口。当前并不是“让模型随意操作数据库”，也不要求用 MCP 来运行平台内的每道听力题。

## 1. 把 AI 放进有反馈的学习流程

**解决的问题：** 单独展示词义或播放单词，很难练习用户能否在语境里识别这个词。用户录入的词义也可能不准确，直接拿来出题会放大原始错误。

**项目做法：** 从已有词库选择词条，先校验并看词复习，再生成场景。页面显示英文缺口，音频朗读包含答案的完整句子；中文提示默认隐藏，用户主动查看或在反馈阶段理解语境。提交之后再结合答案、词形和解析复查。

```text
已有词：effective，形容词，“有效的”
教学题干：The new method improved the ______ of our training.
完整音频：The new method improved the effectiveness of our training.
目标答案：effectiveness，名词，“有效性”
```

这道构造题练的是从 effective 理解其派生名词 effectiveness。词形可以变化，但不能仅因 efficient 意思接近，就把它算作同一词族。

后端入口在 `nestjs/src/interface/ai-services/ai-services.service.ts`，前端在 `react-font/apps/english-world/src/aiListening/AiListeningPage.tsx`。值得复用的是“已有知识→情境任务→提交→反馈”的闭环；是否比其他练习更有效，还需要学习数据和对照评估，不能由功能设计直接推出。

继续阅读：[场景听力完整流程](/ai/listening-flow)、[从单词到听力题](/ai/word-to-question)。

## 2. 将模型输出分层校验，而不只依赖提示词

**知识原理：** 网络请求成功、JSON 可解析、字段符合结构、内容适合教学，是不同层面的判断。

**项目做法：** DeepSeek 请求要求 JSON 输出，把词条视为不可信数据；服务端继续检查返回类型、词条 ID 和结果数量。生成场景时检查题目结构，再发起一次独立的语义复核调用，涉及词形变化时要求对应的关系证明。复核未通过就不能进入正常听力状态。

可把验收问题拆成四层：

| 层次 | 需要回答的问题 | 失败示例 |
|---|---|---|
| 传输 | 是否收到可处理的响应？ | 超时、上游错误 |
| 结构 | 是否能解析，字段与数量是否符合预期？ | 缺一个目标词、重复 ID |
| 业务 | 题干、答案和原词是否满足练习约束？ | 无缺口、答案不属于该词族 |
| 语义 | 表达自然、词义和词形关系是否合理？ | 格式正确但词形解释错误 |

源码重点是 `ai-services.service.ts` 的 `deepseek`、`check` 和 `ready`，以及 `nestjs/src/interface/ai-services/ai-security.ts` 中的题目验证。

这种分层能阻止一部分坏结果进入流程，但第二次调用仍由模型判断，并不是独立事实来源。模型可能重复犯错；增加复核也增加请求、延迟和费用。未来可在高频词形上补充可审定的词典或规则，再用抽样人工评估检查残余错误。

继续阅读：[DeepSeek 生成与校验](/ai/deepseek)。

## 3. 将语音生成与播放分开，让音频成为可复用资产

**解决的问题：** 用户可能反复听同一道题。每点击一次都重新合成，会增加等待与用量；换了音色却继续复用旧声音，又会造成体验混乱。

**项目做法：** `synthesize` 用账号、文本、内容版本、模型、资源 ID、音色、格式、采样率和朗读指令生成音频缓存键。命中缓存直接读取；未命中才进入语音合成流程。用户维度参与键值，避免把私有音频当成跨账号公共资源。

```text
相同账号 + 相同文本、音色和版本 → 可复用已有音频
相同文本 + 不同音色或内容版本   → 不应命中同一资产
同一段音频 + 浏览器0.8倍播放    → 调整播放速度，无需重新合成
```

音频资产键描述“要什么声音”，付费操作键描述“这一次尝试”。代码对结果未知的操作保留 `unknown` 状态，避免把“没收到结果”简单解释成“可以无代价重试”。

实现位于 `nestjs/src/interface/ai-services/ai-services.service.ts` 的 `synthesize`、`claimOperation`，以及前端 `aiListening/audio.ts`。缓存命中只能说明已有资产可取，不能用来证明供应商当前连通或发音一定正确。缓存也带来存储、版本失效和清理问题，需要随数据规模继续治理。

继续阅读：[豆包语音合成](/ai/doubao)。

## 4. 把 AI 配置与成本控制做成管理能力

**解决的问题：** 模型与语音服务职责不同，使用频率也不同。如果共用一份隐藏的配额，用户只会看到“AI 已达上限”，却无法定位和调整。

**项目做法：** DeepSeek 与豆包分别保存有效的用量和并发限制，全局并发另行控制；管理端可以配置服务、测试连接并查看本地用量记录。请求、字符、Token、缓存命中和失败记录分别表达不同信息，不能混成一个“调用次数”。

请求频率、每日请求和每日字符等支持零值关闭相应限制；并发和尝试次数有各自的有效范围，不能笼统地认为所有字段填零都表示无限制。平台保护规则与供应商账户额度也必须区分。

配置保存涉及可恢复的供应商密钥，后端 `ai-security.ts` 使用 AES-256-GCM 加密；加密主密钥应独立保护，数据库加密不代表前端、日志或运维配置可以公开。

代码落点是 `ai-services.service.ts`、`ai-limits.ts` 和 `ai-security.ts`。本地用量便于排障与管理，但不能代替服务商账单，也不能在没有一致口径的情况下推算真实成本或节省比例。

继续阅读：[配置项与错误码](/reference/configuration)。

## 5. 用 MCP 将词库能力开放为受控工具

**知识原理：** 模型理解用户意图，客户端发现并调度工具，服务器执行自己的业务规则。MCP 提供连接和工具调用方式，账号隔离与删除策略仍由产品实现。

**项目做法：** 平台提供查询、读取、新增，以及更新和删除的预览/确认工具。授权绑定账号、作用域和有效期，可以撤销；完整令牌只在创建时展示，数据库保存令牌摘要。查询从授权主体取得账号条件，工具参数不开放任意 userId。

```json
{
  "name": "query_words",
  "arguments": { "keyword": "effective", "limit": 5, "offset": 0 }
}
```

这是工具调用参数示意，不是完整 HTTP 协议报文。客户端还需要完成初始化及授权；返回中没有匹配项也属于正常查询结果。

入口位于 `nestjs/src/interface/mcp-access/mcp.controller.ts`，权限与业务在 `mcp.service.ts`。这一设计让支持对应传输和认证方式的客户端复用词库能力，但不能承诺“任何模型直接填地址就能用”。当前采用独立 Bearer 授权，不能把它写成已经实现 OAuth。

继续阅读：[MCP 如何连接业务系统](/mcp/connection)、[实现 query_words](/mcp/query-words)、[接入 Codex 与排错](/mcp/clients)。

## 6. 预览、事务与幂等让修改更可信

**解决的问题：** AI 可能理解错更新范围，用户也可能在提交后断网。如果重试导致覆盖次数重复增加，单纯的“保存成功”提示无法建立信任。

**项目做法：** 更新先展示前后值和变化字段，再由明确确认执行；确认时检查当前词条是否已变化。确认写入通过事务处理，使用请求 ID 和载荷摘要复用成功结果；同一编号换了内容则拒绝。覆盖还复用空值保护逻辑，避免不完整补全清掉已有信息。

```text
用户确认一次覆盖 → 事务提交，计数增加一次
响应途中丢失     → 客户端不知道是否完成
相同意图有限重试 → 查询并复用已有结果，避免再次计数
词条已发生变化   → 重新预览，不能强行应用旧确认
```

这里的幂等是具体接口、授权和请求标识下的业务保证，不等于所有外部 AI 付费调用都能恰好执行一次。预览凭证也不是长期授权；它仍受版本、有效期和权限约束。

源码在 `mcp.service.ts` 和 `nestjs/src/interface/english/safe-overwrite.ts`。验证时应读取隔离数据库最终记录和覆盖次数，不能只比较两次 HTTP 状态。

继续阅读：[新增与覆盖更新](/mcp/write-workflow)、[事务、并发与幂等](/backend/transactions-idempotency)、[断网重试实例](/backend/retry-example)。

## 7. 把“收到音频”和“正在播放”做成不同状态

**解决的问题：** 按钮点下去后没有反馈、缓冲中却显示播放完成，或用户切题后旧请求又响起来，都会破坏听力体验。

**项目做法：** 播放模块维护 `loading`、`playing`、`idle`，依据实际音频事件更新；新播放会停止旧播放，并取消旧请求。`generation` 标识让过期响应失效，结束后回收 Blob URL。支持的浏览器还会解码检查静音或坏音频，但这不负责判断单词是否读准。

一个可复现的检查场景是：先点击题目 A，音频尚未返回时切换题目 B。最终应该只播放 B，A 的迟到响应不能重新启动，也不能覆盖 B 的状态。这里既需要取消请求，也需要防止已经在处理中的旧异步结果生效。

实现位于 `react-font/apps/english-world/src/aiListening/audio.ts`。前端状态机应表达实际发生的事件；API 成功、音频可解码、设备真正出声、发音适合教学，还需要分别判断。

继续阅读：[播放状态与一次性密钥弹窗](/frontend/playback-and-secret)、[React 页面与状态](/frontend/react-state)。

## 8. 让文档和验证成为交付的一部分

**知识原理：** 代码、需求、测试和文档回答不同的问题。代码说明当前实现，PRD 描述确认过的预期，测试证明某次输入下发生了什么，公开教程帮助读者理解和复现。

**项目做法：** PRD 使用统一目录和索引；文档站独立构建，公开正文与内部需求、日志、私有材料分开。关键代码精选记录来源路径和版本，通过显式命令同步。CI 把文档与应用静态产物一起带入镜像，并校验文档深链与404。

HTTPS、Nginx 和 PWA 共同影响读者能否看到新页面：服务器已经发布，并不等于旧浏览器已经切换版本。更新提示需尊重学习活动，静态文档路径也不能被平台的离线 SPA 回退接管。

维护入口包括 `react-font/apps/docs/`、`scripts/sync-docs-code.mjs`、`scripts/install-docs-nginx.py`、`.github/workflows/deploy.yml`，以及项目的文档维护技能。文档构建通过不等于所有业务验收通过；测试替身成功也不等于真实供应商语音或内容质量合格。

继续阅读：[发布、验证与回滚](/deploy/release-rollback)、[为什么仍然看到旧页面](/deploy/stale-page)。

## 如何把这些经验用于下一个 AI 项目

| 面对的问题 | 可以借鉴的设计 | 仍需补足的证据 |
|---|---|---|
| 模型输出不稳定 | 结构检查、业务约束、语义复核和失败反馈 | 错误率抽样、词典依据、人工评估 |
| 外部服务等待与费用 | 音频资产缓存、独立配额、并发与操作状态 | 真实时延、命中率、账单对齐 |
| AI 要修改用户数据 | 账号隔离、最小作用域、预览确认、幂等 | 越权、并发、撤销和重试边界测试 |
| 异步交互难理解 | 事件驱动状态、过期响应隔离、资源清理 | 慢网、切页、连续点击与设备验证 |
| 功能变了文档没变 | 代码与文档同任务维护、可追溯实例、构建与页面检查 | 持续的内容审查和真实运行证据 |

项目已有这些机制的代码基础。更成熟的下一步应由测量决定：建立内容质量样本、观察生成和播放延迟、对齐实际成本、评估学习反馈，并持续验证权限与恢复能力。本文不把这些待验证方向写成已经取得的收益。

初次阅读可从[本地运行](/start/local-development)开始；理解 AI 主线后，沿各节链接深入实现和实验。公开文档不读取读者的词库、笔记或令牌，文中示例也不会自动执行任何付费调用或生产写入。
