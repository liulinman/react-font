# English World UX Skill 未加载基线评估

## 1. 测试目的与边界

本次测试用于记录未加载项目专属 UX Skill 时，基线 Agent 对 English
World 标准 Context Lab 流程的审计能力和遗漏模式。

盲测期间只读取了 `apps/english-world` 下与该流程相关的前端源码、测试和
应用内文档；未读取 `.agents/skills`，未读取本项目的 UX Skill 设计文档，
也未读取后续实施计划中的结论。

## 2. 原始审计提示

```text
请只读审计 English World 的“用户生成一个标准 Context Lab 练习并开始作答”
流程。检查现有前端源码、测试和文档，输出体验问题与改进需求，不要修改文件。
```

## 3. 基线 Agent 审计摘要

以下内容保留未加载专属 Skill 时的直接审计形态：能发现若干真实问题，但没有
统一的证据分级、严重度、置信度和验收格式。

### 3.1 流程概览

- 桌面端从 `/englishWorld/context-lab` 进入，用户选择词汇来源、数量、
  IELTS 难度和模型后提交异步生成任务。任务进入练习包历史，通过 SSE 更新
  `pending`、`processing`、`succeeded` 或 `failed` 状态；成功后可以打开
  练习弹窗并作答。
- 移动端从 `/englishWorldMobile` 的语境练习入口进入独立 Context Lab 页面，
  同样先生成异步任务，再从练习包列表开始作答。
- 提交答案后，桌面端和移动端都能显示得分、错题、解析、薄弱词和后续建议；
  历史记录支持查看既往提交详情。

### 3.2 发现的体验问题

1. **标准任务可能永久停在旧状态，且用户不知道实时更新已经失效。**
   `subscribeContextLabTaskEvents` 只建立一次流式连接，连接结束或报错后不重连；
   标准流程也没有像 micro 流程一样轮询详情。桌面端和移动端订阅时均未传入
   `onError`，因此断流不会产生可见提示。用户只能自己发现状态不再变化，再从
   刷新按钮或桌面端任务的更多菜单手动刷新。

2. **失败项的“重新生成”不一定重试原任务。**
   桌面端失败卡片点击“重新生成”会直接调用当前页面的 `handleGenerate`。
   该函数使用此刻生成表单的 `requestBody`，而不是失败任务原来的来源、词组、
   难度、模型或粘贴材料。用户修改过表单后，按钮看似重试失败任务，实际可能
   创建一份内容完全不同的新任务。

3. **创建成功后的历史刷新失败会产生互相矛盾的反馈。**
   桌面端在创建接口成功后先提示“生成任务已提交”，随后等待 `loadHistory`。
   如果历史接口失败，`loadHistory` 自己提示“历史记录加载失败”，外层又会把
   同一次操作提示为“任务提交失败”，而任务实际上已经创建并被乐观加入列表。

4. **生成前的输入校验和提交确认不一致。**
   移动端手输词要求至少三个，桌面端却可以把空数组或不足三个词直接提交；
   桌面端只对粘贴材料是否为空做前置校验。提交前也没有汇总本次将使用的词源、
   词数、难度和模型，用户难以在长时间生成前确认参数是否符合预期。

5. **粘贴材料生成的历史项可能没有可识别标题。**
   历史卡片标题固定来自 `task.words`。粘贴文章任务可以返回空词组，此时桌面端
   和移动端都会出现空标题以及“0 个词”，用户无法仅凭列表识别是哪篇材料。

6. **历史列表会静默截断，搜索结果数量也可能误导。**
   桌面端固定请求前 10 条，移动端固定请求前 20 条，没有分页或“加载更多”。
   桌面端搜索摘要展示的是当前返回数组长度，而不是接口提供的 `total`，因此
   “找到 N 个练习包”不一定代表完整结果。

7. **开始作答后没有草稿恢复或离开保护。**
   答案只保存在组件内存。桌面端关闭练习弹窗后，再从历史点击“开始练习”会
   清空答案；移动端点击返回再重新打开也会清空答案。刷新页面、切换路由或
   组件卸载同样没有恢复机制，也没有在存在未提交答案时确认用户是否要离开。

8. **桌面端提交后的状态语义不清楚。**
   提交成功后解析和结果已出现，但选项仍可修改，提交按钮也继续显示。用户可以
   改变屏幕上的答案，而解析仍对应上一次提交；再次点击提交究竟是覆盖、重试
   还是新增一次 attempt，没有明确说明。移动端则会锁定选项并隐藏提交按钮，
   两端行为不一致。

9. **移动端对失败与恢复的支持明显弱于桌面端。**
   移动端失败任务只显示“生成失败”，不展示 `errorMessage`，也没有重新生成
   操作；活动任务仍显示删除按钮。移动端提交成功后不刷新练习包历史，因此返回
   列表时最近得分和练习次数可能仍是旧值。

10. **现有测试主要证明理想路径可运行，没有保护关键恢复路径。**
    桌面端单测覆盖创建、SSE 成功更新、历史、提交和结果复盘，E2E 覆盖手动刷新
    后开始练习；移动端单测覆盖创建、SSE 成功更新、提交和历史详情。但没有测试
    标准任务断流或长等待、失败任务按原参数重试、创建成功但历史刷新失败、
    作答中离开与刷新恢复、提交失败后的连续性、粘贴材料空标题，以及移动端失败
    原因和重试。移动端 Cypress 测试只验证外壳导航和横向溢出，没有走 Context
    Lab 的生成到作答旅程。

11. **应用内文档不能作为该流程的产品规格。**
    `REFACTOR_NOTES.md` 只概述 English World 重构重点；移动端 `README.md`
    主要描述单词管理功能，且声称与 PC 功能相同，但没有定义 Context Lab 的
    生成、等待、失败、恢复和成功标准。

### 3.3 基线 Agent 给出的改进需求

- 为标准任务增加 SSE 重连或详情轮询兜底；断流时显示持久状态，并把刷新操作
  放在当前任务附近。
- 让失败任务的重试使用原始生成参数，或把原参数恢复到表单并明确要求用户确认
  后再生成。
- 分离“任务创建”和“历史刷新”的错误反馈，避免已创建任务被描述成提交失败。
- 统一桌面端与移动端的手输词校验，并在提交前显示本次生成参数摘要。
- 为粘贴材料任务生成可识别的历史标题，并为历史增加分页或加载更多。
- 自动保存未提交答案；关闭、返回、刷新或切换任务时提供继续作答入口或离开确认。
- 明确提交后是锁定本次结果还是允许开始新一次练习，并统一桌面端与移动端行为。
- 移动端展示失败原因和重试操作，阻止删除活动任务，并在提交后刷新历史摘要。
- 增加覆盖断流、失败、重试、恢复和移动端完整旅程的测试。

## 4. 对照任务说明的遗漏项

| 检查项 | 基线表现 | 评估 |
| --- | --- | --- |
| 是否读取已有规格 | 只读取应用内 README 和重构说明，没有找到或读取可定义该旅程的产品规格，也没有在开始审计前把“规格缺失”声明为证据限制。 | 遗漏 |
| 是否定义任务开始和成功状态 | 描述了入口、生成完成和提交结果，但没有先声明“任务从哪里开始”“开始作答的成功条件是什么”“哪些情况算失败或部分成功”。 | 部分遗漏 |
| 是否区分事实、观察和推断 | 源码行为、测试缺口和用户影响写在同一层级，没有为每条结论标注事实、观察或推断。 | 遗漏 |
| 是否检查生成等待、失败、重试、历史和恢复 | 覆盖了等待断流、失败重试、历史截断和作答恢复，也检查了测试缺口；但没有用统一状态矩阵逐一验证每个状态、转移和离开路径。 | 部分满足 |
| 是否同时覆盖桌面端与移动端 | 同时检查了桌面路由、响应式样式、独立移动端页面和相应测试，并发现两端行为不一致。 | 满足 |
| 是否给出严重度、置信度和可验收需求 | 只给出问题和方向性需求，没有严重度、置信度，也没有 Given/When/Then 或可直接转成测试的验收条件。 | 遗漏 |
| 是否避免把视觉偏好写成高优先级需求 | 结论集中在任务可靠性、状态可见性、数据一致性和恢复能力，没有把个人视觉偏好提升为高优先级问题。 | 满足 |

### 4.1 其他基线不合格模式

- 没有建立“规格要求 -> 前端实现 -> 测试覆盖 -> 发现”的追踪关系。
- 没有说明哪些判断仅来自静态阅读，哪些已经通过运行时或真实视口验证。
- 没有为桌面响应式 Context Lab 与 `/englishWorldMobile` 独立实现分别定义
  测试对象，容易把“有移动样式”误当成“移动旅程已验收”。
- 没有按用户损失、发生概率、可恢复性和影响范围解释优先级。
- 改进需求仍是方向性表述，开发人员需要二次解释才能写测试或验收。

## 5. 应由项目专属 Skill 强制执行的规则

1. **先建立审计契约。**
   在读取实现前记录用户旅程、用户角色、入口、任务开始状态、成功状态、失败状态、
   范围外事项和待验证假设。若规格不存在或因边界不能读取，必须明确标注，不得把
   当前实现自动当成产品要求。

2. **先读规格，再读实现和测试。**
   按“产品规格与设计说明 -> 路由和页面 -> 状态与接口 -> 单元测试 -> E2E 与视觉
   测试 -> 应用文档”的顺序取证，并为每条发现保留文件和行号。

3. **强制区分证据类型。**
   每条结论必须分别写出“事实”“观察”“推断”。事实来自规格、源码或测试；
   观察来自运行时或截图；推断必须说明依据和仍需验证的部分。

4. **强制建立状态与恢复矩阵。**
   至少检查初始、校验、提交中、等待、长等待、成功、失败、重试、历史、开始作答、
   部分作答、提交中、提交失败、提交成功、关闭、返回、刷新、断网、重连和跨设备
   恢复。每个状态都要检查用户看到什么、能做什么、数据是否保留、如何恢复。

5. **强制覆盖桌面端和移动端。**
   分别检查桌面宽屏、窄屏响应式页面和独立移动端实现；不能用 CSS 断点或单个标题
   可见性代替完整旅程验证。两端若行为不同，必须说明差异是有意设计还是缺口。

6. **统一发现格式。**
   每条发现必须包含：编号、旅程阶段、证据、用户影响、严重度、置信度、改进需求、
   验收条件和建议测试层级。严重度应基于任务阻断、数据丢失、错误操作、可恢复性
   和影响范围，不得仅基于视觉喜好。

7. **需求必须可验收。**
   避免“优化体验”“加强提示”等表述。需求必须描述触发条件、界面反馈、允许操作、
   数据保留、超时或失败行为和成功结果，并能直接转成单测或 E2E 断言。

8. **视觉问题必须证明用户影响。**
   只有在遮挡、溢出、不可读、触控目标不足、焦点不可达、对比度不合格或阻断任务
   时，视觉问题才可列为高优先级；纯审美偏好默认不进入高优先级需求。

9. **强制审查测试的反证能力。**
   不只统计已有测试，还要列出测试没有证明什么。异步生成流程必须包含失败、断流、
   超时、重试参数一致性、刷新恢复、重复提交和移动端完整旅程。

10. **输出前执行完整性门禁。**
    若缺少规格读取、开始与成功定义、事实/观察/推断标签、状态矩阵、双端覆盖、
    严重度、置信度或验收条件，审计不得标记为完成。
