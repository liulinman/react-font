# English World 桌面录词 AI 原形与拼写纠错设计

## 背景与目标

桌面端“添加单词”弹窗已经会在用户停止输入后调用 Word Agent，并自动补充空白的音标、中文释义和词性。现有接口虽然可能把屈折形式返回为词典原形，但前端只能通过字符串相似度猜测返回结果是否相关，无法区分“合法原形”“词形变化”“拼写错误”和“不确定结果”，也无法让用户明确确认纠正。

本次优化让 Word Agent 在同一次查询中返回结构化输入诊断。桌面端根据诊断显示原形或拼写建议，由用户选择“使用建议”或“保留原词”。系统不静默替换单词、不阻止保存，也不覆盖用户已经手填的字段。

本设计中的“原形”指词典 lemma，而不是词根或派生词基底。例如 `running` 建议为 `run`，但 `happiness` 是独立的合法词条，不应改成 `happy`。

## 范围

本次包含：

- 扩展现有 Word Agent 返回结构和提示词。
- 升级 Word Agent Redis 缓存版本。
- 在桌面端新增词条弹窗中展示并处理 AI 纠正建议。
- 为后端诊断、缓存和桌面端交互补充自动化测试。
- 完成前后端部署及生产环境验证。

本次不修改编辑词条流程、移动端新增流程、批量导入、笔记字段、数据库结构或保存接口。

## 方案选择

采用“扩展现有 Word Agent 返回结构”的方案。原形判断、拼写判断和词条资料由同一次 AI 调用生成，避免额外请求的延迟与成本，并让前端直接消费明确状态。

未采用以下方案：

- 前端根据输入和返回词的编辑距离推断：对不规则变化、首字母拼错和合法近形词不可靠。
- 新增独立校验接口：会增加一次 AI 调用、响应时间和前后端状态协调成本。

## API 合同

`WordAgentItem` 新增两个字段：

```ts
type WordAgentInputStatus =
  | "exact"
  | "inflected"
  | "misspelled"
  | "uncertain";

interface WordAgentItem {
  // existing fields
  inputStatus: WordAgentInputStatus;
  correctionReason: string;
}
```

字段语义如下：

- `exact`：输入是可独立收录的标准英文词典词条，或是需要原样保留的英文短语。`word` 与规范化后的输入相同。
- `inflected`：输入是合法屈折形式，例如复数、第三人称单数、进行时、过去式、过去分词或比较级；`word` 是对应 lemma。
- `misspelled`：输入很可能存在拼写错误；`word` 是 AI 最有把握的正确拼写，并且为词典 lemma。
- `uncertain`：无法可靠判断、存在多个同等可能候选，或输入不适合进行英文单词纠正。前端不得据此提出替换。

`correctionReason` 使用简短中文说明，仅在 `inflected` 或 `misspelled` 时必填，例如“这是 run 的现在分词”或“常见拼写错误，i 和 e 顺序颠倒”。`exact` 和 `uncertain` 返回空字符串。理由只解释判断，不生成学习笔记，也不持久化到词条数据中。

英文输入在比较前去除首尾空白、合并连续空格并忽略大小写。单个词中的连字符和撇号继续按现有英文输入规则处理。英文多词短语必须原样保留为完整短语并返回 `exact`，不得只返回首词或对短语内部单词做 lemma 替换。中文输入和其他非英文输入继续保留 Word Agent 原有查询能力，但诊断状态为 `uncertain`；本次桌面新增弹窗不会为其显示纠正建议。

## 后端设计

### 提示词与结果映射

现有 Word Agent 系统提示词增加四种状态的定义、示例和 JSON 字段约束。提示词明确要求：

- 区分屈折变化和派生词，合法派生词不得被还原成另一个词。
- 只有在存在单一、高置信候选时才能返回 `misspelled`。
- 无法可靠判断时返回 `uncertain`，不得编造纠正结果。
- `word`、释义、音标、词性和例句必须全部对应最终候选词。

生产验证后，AI 原始结果还必须增加只供后端校验的 `sourceWord` 和 `wordFormType`。`wordFormType` 只能是：

- `base`
- `plural`
- `third_person_singular`
- `past_tense`
- `past_participle`
- `present_participle`
- `gerund`
- `comparative`
- `superlative`
- `possessive`
- `spelling_error`
- `unknown`

提示词必须明确给出 `running → run / present_participle`、`went → go / past_tense`、`insects → insect / plural` 和 `recieve → receive / spelling_error`，并说明即使 `running` 等词形也可以作名词或形容词，只要当前输入是常见屈折形式，仍优先返回 lemma。合法派生词如 `happiness` 必须返回 `base`，不能还原为 `happy`。

服务层增加独立的诊断归一化边界，在将每个 AI 结果与对应输入配对后校验状态和候选：

- 未知或缺失的状态统一降级为 `uncertain`。
- `inflected` 或 `misspelled` 的候选必须是非空英文单词，并且与输入不同；不满足时降级为 `uncertain`。
- AI 把不同候选标为 `exact` 时降级为 `uncertain`，避免前端错误自动补全。
- AI 返回的候选与输入实际相同时，将错误标注的 `inflected` 或 `misspelled` 归一为 `exact`。
- 英文短语继续使用现有完整性保护；最终强制保留规范化后的原短语并标为 `exact`。
- `correctionReason` 去除首尾空白；非纠正状态清空理由，纠正状态缺少理由时由服务层提供通用短句。
- `sourceWord` 必须与对应输入规范化后完全一致，否则结果降级为 `uncertain`。
- 只有受控屈折类型配合“与输入不同的合法候选词”才能生成 `inflected`；`spelling_error` 配合不同候选词才能生成 `misspelled`。
- `base` 只能配合同词结果生成 `exact`。同词却声明为屈折类型、异词却声明为 `base`、未知类型或其他矛盾组合统一降级为 `uncertain`。
- `uncertain` 和矛盾结果可以返回给当前请求，但不得写入 Redis，避免一次模型异常被缓存放大。

这个边界同时应用于普通查询、批量查询和流式查询的最终结果，保证不同入口写入缓存的数据结构一致。

### 缓存与兼容性

Redis key 前缀升级为 `word-agent:v3:`。v2 已在首次生产部署中写入过 `running / exact` 的错误诊断，因此 v3 同时承载新的词形类型合同并让错误 v2 记录立即失效。缓存校验器要求 `inputStatus` 为四个合法枚举值、`correctionReason` 为字符串。旧缓存自然失效，不执行扫描或迁移，继续沿用现有七天 TTL。

接口变更为增加字段，现有调用方可以忽略它们。部署顺序为先后端、后前端。桌面前端在迁移期允许字段缺失：缺失诊断时不显示纠正建议；只有返回词与输入规范化后完全相同时，才沿用原有空白字段自动补全。它不会恢复编辑距离纠正逻辑，因此即使后端暂时回滚，也不会错误替换词条。

## 桌面端交互设计

### 查询触发

仅在桌面端新增模式启用。用户输入停止 600ms 后，沿用现有英文输入预检并调用 `/word-agent/query`。明显不是英文词条的输入不发起请求；请求期间继续在输入框尾部显示加载状态。

每次修改单词时：

- 立即清除上一输入对应的建议和“保留原词”决定。
- 增加请求序号；晚于新输入返回的旧结果直接丢弃。
- 保持用户已经填写的释义、音标、词性、笔记和其他字段不变。

### 四种结果

- `exact`：不显示纠正条，沿用现有行为，仅自动补充尚为空白的音标、中文释义和词性。
- `inflected`：在单词输入框下方显示紧凑提示，例如“检测到词形变化：`running → run`”，并显示 AI 理由。
- `misspelled`：在相同位置显示“可能拼写错误：`recieve → receive`”，并显示 AI 理由。
- `uncertain`：不显示纠正条，也不使用候选词资料自动补全。

纠正条提供“使用建议”和“保留原词”两个明确操作。提示属于辅助信息，不作为表单校验错误；用户可以不处理提示而直接保存当前输入。

### 使用建议

点击“使用建议”后：

1. 将 `englishWord` 替换为 AI 返回的 `word`。
2. 使用同一次 AI 返回结果补充仍为空白的音标、中文释义和词性。
3. 不覆盖用户已经手填的任何字段。
4. 根据最终候选重新计算现有单词/短语类型默认值，但保留用户明确修改过的类型。
5. 关闭纠正条，并把候选登记为本次已完成查询，避免替换动作立即触发重复 AI 请求。

### 保留原词

点击“保留原词”后关闭当前提示，保持输入和所有手填字段不变，不把候选词的音标、释义或词性填入原词。该决定只绑定当前规范化输入；用户再次修改单词后会重新检测。

## 前端组件与状态边界

Word Agent 客户端类型增加可选诊断字段以支持前后端分步部署。桌面新增弹窗维护一个待确认建议对象，包含查询输入、候选 `WordAgentItem` 和诊断状态。

现有 AI 补全逻辑拆分为三个职责清晰的纯函数：

- 输入和响应归一化：验证状态、输入与候选的对应关系，决定自动补全、显示建议或忽略结果。
- 空白字段补丁构建：复用现有不覆盖手填内容的规则。
- 建议操作：分别生成“采用候选”和“保留输入”的状态变化。

纠正条作为弹窗内部的小型展示组件，只接收输入、候选、状态、理由和两个回调，不直接请求接口或提交表单。这样可以独立测试文案与按钮行为，也避免继续扩大表单副作用的范围。

## 异常与边界处理

- AI 请求失败、超时或返回空数组：不显示纠正条，不阻止用户填写和保存；保留现有非阻塞失败提示。
- 状态缺失、枚举非法或候选格式非法：按 `uncertain` 处理。
- 请求返回时输入已经变化、弹窗已关闭或已切换为编辑模式：忽略结果。
- 用户在等待期间手填其他字段：后续自动补全或采用建议仍只填写空白字段。
- 用户在建议出现时直接保存：按输入框当前原词保存，不进行隐式替换。
- 合法不规则屈折形式由 AI 返回 `inflected`，例如 `went → go`，不依赖字符相似度。
- 首字母拼错等情况可以返回 `misspelled`，不再受旧的“首字母必须一致”规则限制。
- 合法派生词、缩写、专有名词或罕见词只有在 AI 能确认其为独立词条时返回 `exact`；否则返回 `uncertain`，而不是强行纠正。
- 英文短语始终按完整词条处理，不展示 lemma 纠正。
- 笔记、图片、引用和原始输入历史均不由纠正功能自动写入。

## 测试方案

### 后端单元测试

- 正常原形返回 `exact`，资料与原词对应。
- 规则与不规则屈折形式返回 `inflected` 和 lemma。
- 明确拼错返回 `misspelled` 和唯一候选。
- 合法派生词保持 `exact`，不被还原为词根相关词。
- 不确定、缺失或非法状态安全降级。
- 错误的状态/候选组合经过服务层归一化。
- 英文短语保持完整、标为 `exact`，普通和流式路径一致。
- `running → run / present_participle`、`went → go / past_tense`、复数和拼写错误通过受控类型校验。
- 同词屈折、异词 `base`、错误 `sourceWord` 和未知类型降级为 `uncertain` 且不缓存。
- 缓存只接受完整 v3 结构，并使用 `word-agent:v3:` key。
- 缓存命中、未命中、重复输入和 Redis 故障继续保持现有行为。

### 桌面组件测试

- `exact` 结果自动补全空白字段且不显示建议。
- `inflected` 结果显示原形建议，出现提示时不提前填入候选资料。
- `misspelled` 结果显示拼写建议。
- 点击“使用建议”替换单词并只补充空白字段，不重复请求候选词。
- 点击“保留原词”不改变单词或手填字段；修改单词后可重新提示。
- 用户不处理提示仍可提交当前输入。
- 晚到的旧响应不会覆盖新输入对应的状态。
- `uncertain`、非法响应、请求失败和明显非英文输入不会阻断表单。
- 诊断字段缺失时，只允许完全同词的旧响应自动补全，不显示纠正建议。
- 编辑模式和移动端行为没有变化。

### 验证与部署

1. 运行 NestJS Word Agent service/cache 测试和后端构建。
2. 运行 English World 弹窗相关 Vitest、应用测试和生产构建。
3. 先部署后端，确认生产接口返回 v3 合同生成的诊断字段并且旧前端正常使用。
4. 再部署前端，在桌面端手工验证 `confront`、`running`、`went`、`recieve`、`happiness`、`be cited as` 和一个不确定输入。
5. 验证“使用建议”“保留原词”、直接保存、已有字段不覆盖以及请求失败降级。

## 成功标准

- 桌面端能明确区分并提示词形变化和高置信拼写错误。
- 任何单词替换都必须由用户主动确认。
- AI 不确定或不可用时，新增和保存流程仍然可用。
- 候选资料不会错误填入用户选择保留的原词。
- 不依赖编辑距离即可处理不规则变化和首字母拼错。
- 前后端测试、构建和生产验证全部通过。

## 非目标

- 不保存原始输入或纠正历史。
- 不把 AI 理由写入笔记。
- 不提供多个候选词、候选排序或“撤销纠正”历史。
- 不新增独立拼写检查接口或第二次 AI 调用。
- 不修改移动端、编辑模式或批量导入纠错逻辑。
- 不对用户选择保留的输入施加保存限制。
