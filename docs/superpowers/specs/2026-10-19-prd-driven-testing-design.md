# PRD 驱动的模块测试闭环

日期：2026-10-19。状态：已授权并接入；PRD 全量自动化覆盖仍待逐项完善。执行入口见 [使用说明](../../testing/prd-testing.md)。

## 目标与入口

用户在当前 Codex 中说“测试阅读模块”“测试词库和复习”或“全量验收”。AI 读取登记的 PRD，生成或更新可追踪 Case，实现缺失脚本，运行隔离环境中的测试，生成报告，再依据需求、代码、截图和日志分析失败原因。只执行已有脚本不等于完成这条闭环。

默认手动触发；本次不增加定时自动化，不改动生产部署，不提交或推送用户现有变更。Push 冒烟属于可后续接入的辅助执行入口，不替代本次验收。

## 模块边界

模块按用户可完成的业务任务划分，使用稳定 ID。桌面、移动端、后台是端与角色标签，不单独把同一业务拆成三套需求。某个模块的测试必须包含 PRD 明确要求的相关端与权限。

| ID | 中文名与别名 | 业务边界 |
|---|---|---|
| auth | 登录与权限、账号 | 登录、退出、会话、访问控制；其他模块各自验证资源权限 |
| vocabulary | 词库与导入、词库、单词 | 词条查询、筛选、编辑、批量操作、AI 词条、导入冲突与来源文件 |
| review | 学习与复习、复习、学习 | 今日复习、学习会话、提交、恢复、薄弱词与记忆地图 |
| context | 语境练习、Context Lab | 生成任务、选词来源、练习、历史、IELTS 语境题型 |
| reading | 阅读练习、阅读 | 后台导入编辑审核发布、接收人、用户作答、解析、阅读成绩分析 |
| notes | 知识笔记、笔记 | 长笔记、独立笔记、关联词条、文件夹、复制整理 |
| word-books | 复习册、单词册 | 创建、浏览、管理、知识整理、打印 |
| notifications | 通知与公告、通知 | 公告发布、通知接收、未读与跳转 |
| settings | 设置与站点、设置 | 用户设置、主题、站点导航、通用布局与安装离线能力 |

“全量”展开为全部登记模块，不能只展开为已有脚本。每个 PRD 验收项只有一个主要归属模块，可附多个影响标签。跨模块 Case 关联多个模块，选任意关联模块都包含它，同一运行按 Case ID 去重。比如“阅读发布通知”主要归阅读，同时标通知；阅读和通知一起运行只执行一次。

复习册明确独立于今日复习；阅读练习明确独立于 Context Lab。管理后台中的阅读功能归阅读，公告归通知。尚未归属或缺少 PRD 的功能作为范围缺口报告，不凭代码补造需求。

## 需求来源与覆盖

需求唯一入口已统一为 `docs/prd/README.md`，模块及功能归属登记在 `docs/prd/index.json`。测试侧的 `docs/testing/modules.json` 只引用这些稳定模块 ID，补充别名、脚本入口和环境类型，不另行维护一套 PRD 来源。文件路径相对仓库解析，不依赖开发者机器绝对路径。

已找到的来源包括：

- 知识笔记：`docs/prd/notes/prd.md` 汇总独立笔记与文件夹 PRD。
- 阅读：`docs/prd/reading/prd.md` 汇总接收人、成绩分析 PRD，并链接共享阅读基础设计；基础 PRD 完整性尚待确认。
- 复习册：`docs/prd/word-books/prd.md`。
- 学习与复习：`docs/prd/review/prd.md` 汇总薄弱词修复闭环、词汇掌握轨迹 PRD。
- 其他模块：逐份核对现有 PRD 和已确认设计，不能将日期最新的局部 PRD 当成全产品基线。

正式 PRD 与同目录决策补充均从仓库内统一目录读取；运行时保存其内容快照和哈希。外部设计或历史交付证据仅作补充，缺失时显式记录，不以旧迁移跳转为正文。模块缺 PRD 或完整性未确认时报告需求缺口，不能默默跳过。冲突的需求先标记未决，后续补充只有明确声明覆盖关系才取代旧要求。

AI 逐条盘点所选 PRD 的验收要求，记录来源、原文位置、稳定 AC ID 和优先级；未标优先级的要求保留“未定”，不擅自降级排除。模块选择只限制模块范围；默认覆盖其全部当前验收项，包括异常、权限、数据持久化和 PRD 明示的移动端场景。排除项必须有具体依据。

Case 保存在 `docs/testing/cases/<module>.json`，便于脚本校验，同时生成 Markdown 阅读视图。每条含稳定 Case ID、AC IDs、模块、端、角色、前置条件、数据准备、步骤、可观测断言、清理、执行层级、脚本及测试名称。保留现有 AUTH-001、WORD-001、REVIEW-001 等编号；多层断言通过执行项 ID 区分，不重复计算需求覆盖。

PRD 内容变化时 AI 比对并更新 Case；本次需求快照、Case 快照和两仓库版本锁定后才执行。校验覆盖映射，禁止以生成的 Case 总数充当全部需求数量。

## AI 与确定性执行的分工

项目内新增 Codex 可读取的流程说明和本地项目技能，登记自然语言触发方式。AI 使用当前 Codex 会话，不另接模型服务或保存 API 密钥。

AI 负责：读取原始 PRD、建立验收清单、设计 Case、补充自动化脚本、检查断言有效性、分析证据与相关代码、产出中文分析。程序负责：选择模块、校验映射、建立运行目录、启动服务、调用测试、归档结构化结果、汇总覆盖与渲染报告。

本地执行命令约定：`node scripts/test-prd.mjs --module reading`、`--module vocabulary,review`、`--all`；提供 `--list` 和不启动环境的 `--plan`。这些命令执行已生成并验证的计划；自然语言入口负责在执行前补全 AI 阶段。CLI 不伪装为有 LLM 的独立代理。

缺少 AI 分析时报告显示“待 AI 分析”。没有 PRD、缺少脚本或环境不可用时保留未执行项，并生成不完整报告；不能把它们计为通过。

## 执行环境与脚本接入

复用前端 `scripts/test-local.mjs` 和后端隔离 MySQL/NestJS runner，扩展为可传入明确 spec 清单；维持现有锁、端口检查和异常清理。真实数据只在隔离测试库中生成，不默认访问生产。

先盘点每个现有 spec，明确 mock 页面测试、真实联调测试、组件/单元测试，以及需要 admin 服务、固定账号或专用端口的测试。不能依据目录认定所有 `e2e` 都是 mock。目前部分阅读用例写死管理端 5176，需要参数化且编排 admin 服务之后才能纳入可执行计划。

真实联调需同时记录前端和后端的分支、SHA、dirty 状态及差异哈希；dirty 时在报告明确目标并保留受控变更清单，避免声称验证了一个纯提交版本。mock 场景只能证明页面行为，不能证明真实接口、权限和持久化。真实 AI 依赖与本地 AI 替身分别标识，替身通过不能算真实 AI 联调通过。

Case 脚本复用先于新增；仅在需求没有可执行覆盖时补脚本。AI 不根据当前实现反推预期，不为通过而削弱断言。失败本轮保留；不自动修产品或改 PRD，不自动提交推送。

## 结果与失败分析

每次运行写入被 Git 忽略的 `test-results/prd/<run-id>/`：需求和 Case 快照、范围及排除、计划、前后端版本、命令退出码、逐项机器结果、截图、日志、HTML 报告与 `analysis.md`。运行中断也应尽力归档。凭证不写入快照或报告，日志与附件需按实际内容脱敏。

报告区分：通过、执行失败、未执行/阻塞，并单列未覆盖验收项；只有所选范围的必需验收项全部有有效执行证据且通过，整体才通过。对一个 AC 有多条 Case 时，全部必要断言通过才算 AC 通过。缺脚本、跳过、零条测试、进程启动失败都不能当通过。区分执行完成与验收通过。

失败分析按“产品问题、脚本问题、环境问题、待定位”组织。每项给出需求依据、失败步骤、预期/实际、证据路径、涉及代码、判断置信度和建议；没有根因证据时仅给假设与下一步验证。不得仅凭错误文字宣布根因确定。

本次最小报告为 HTML + JSON + Markdown；PDF 作为后续导出能力，不引入已有个人工具箱的绝对路径依赖。Cypress Cloud 为可选运行记录层；无 Cloud 项目和密钥仍能完整执行本地 AI 流程。未配置就明确显示未接入，不在本次创建外部账户或更改 GitHub Secrets。

## 实施边界与验证

先交付模块登记、Case/AC 格式、项目技能、选择/校验/执行/报告脚本和一条真实模块闭环；其余模块全部出现在覆盖表，逐项接入，最终全量不能因缺覆盖显示通过。首条用知识笔记验证，因为有明确 PRD、文件夹补充和现成浏览器用例；先检查测试环境支持程度。

验证必须包含：中文别名/多模块/全量解析；跨模块去重；未知模块拒绝；PRD 变更检测；缺脚本/空结果/跳过/失败退出码；服务失败及中断的报告归档；mock 与真实证据区分；一次真实启动环境的所选模块执行。不能仅靠 dry-run 宣称完整闭环可用。

保持现有未提交业务代码，不重置工作区。设计确认后形成实施计划，再按可检查的阶段开发；项目技能的发现和具体格式以本机 Codex 能力核实后决定。
